# Security Audit — AI English Teacher Backend

Scope: `apps/api` (Node.js/Express/Prisma/PostgreSQL backend), plus the
supporting `docker-compose.yml` and `scripts/` at the repo root. This backend
is distributed as a source zip for self-hosting, so operators — not just the
original authors — carry responsibility for the deployment-time items in the
checklist below.

Audit date: 2026-10-28. Framework: OWASP Top 10 (2021). This document is maintained for the API backend. The dated addendum `docs/SECURITY_AUDIT_2026-10-28.md` records this branch's fresh dependency scan and evidence limitations.

## OWASP Top 10 (2021) — Risk Mapping

| # | Risk | Mitigations in this codebase | Residual risk |
|---|------|-------------------------------|----------------|
| A01 | Broken Access Control | `src/middleware/auth.js` (`requireAuth`, `requireRole`) enforces authentication and RBAC on every protected router (`src/routes/me.js`, `progress.js`, `economy.js`, `admin.js`, `materials.js` all call `router.use(requireAuth, ...)`). Admin routes additionally require `requireRole('ADMIN')`. Ownership is enforced by scoping all Prisma queries to `req.user.id` (e.g. `src/routes/progress.js`, `economy.js`) rather than trusting client-supplied user ids. Blocked users are rejected at the middleware layer (`auth.js`) and at login/refresh time (`src/routes/auth.js`). | Multi-tenant "teacher can only see their own students" scoping is not implemented — `teacherId` exists on `User` but admin/list endpoints currently return all users to any ADMIN. If teacher-level (non-admin) staff roles are introduced later, add row-level scoping by `teacherId`. |
| A02 | Cryptographic Failures | Passwords hashed with bcrypt cost factor 12 (`src/routes/auth.js`, `BCRYPT_COST = 12`). Refresh tokens are opaque random 48-byte values; only their SHA-256 **hash** is persisted (`src/lib/jwt.js` `generateRefreshToken`/`hashRefreshToken`; `RefreshToken.tokenHash` in `prisma/schema.prisma`) — a stolen DB dump cannot be replayed as a live refresh token. JWTs are signed HS256 with an explicit algorithm allowlist on verify (`src/lib/jwt.js` `verifyAccessToken` pins `algorithms: ['HS256']`), preventing alg-confusion/"none" attacks. `.env.example` documents that `JWT_SECRET` must be long/random. | TLS termination is **not** handled by this application (Express serves plain HTTP) — it is a deployment-time responsibility, see checklist below. No field-level encryption at rest for PII (email, name); acceptable for this data class but should be revisited if more sensitive data is added. |
| A03 | Injection | All database access goes through Prisma Client's parameterized query builder — there is no raw SQL anywhere in `src/` (`grep -r "\$queryRaw\|\$executeRaw" src/` returns nothing). Every request body/query/param is validated and coerced by `zod` schemas via `src/middleware/validate.js` before it reaches a handler (see schemas in every file under `src/routes/`). File uploads are validated by MIME allowlist before any parsing library touches the bytes (`src/lib/textExtract.js` `isAllowedMime`). | Prisma's generated client is the trust boundary; if a future contributor adds `$queryRawUnsafe` with string concatenation, that guarantee breaks — enforce via code review / lint rule. |
| A04 | Insecure Design | Server-side economy caps prevent a modified client from self-awarding unlimited currency (`src/routes/economy.js`, `MAX_XP_PER_CALL = 200`, `MAX_COINS_PER_CALL = 100`, enforced by the `earnSchema` zod max, not just documentation). Spend is wrapped in a Prisma `$transaction` that re-checks the balance server-side immediately before decrementing, closing the check-then-act race window (`src/routes/economy.js` `/spend`). Refresh tokens rotate on every use and the previous token is immediately revoked, limiting the blast radius of a leaked refresh token (`src/routes/auth.js` `/refresh`). Registration can be centrally disabled via the `registrationOpen` setting (`src/routes/auth.js`). | The `$transaction` callback runs against the fake in-memory client in tests and against Prisma's interactive transaction in production; true DB-level row locking (`SELECT ... FOR UPDATE`) is not explicit — under very high concurrency on the *same* user's balance, Prisma's default transaction isolation should still prevent double-spend, but this has not been load-tested against concurrent write bursts. |
| A05 | Security Misconfiguration | `helmet()` is applied globally with an explicit CSP (`default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, etc. — see `src/app.js`). `x-powered-by` is disabled. CORS uses an explicit allowlist parsed from `CORS_ORIGINS`, not a wildcard (`src/app.js`). Error responses never include stack traces when `NODE_ENV=production` (`src/middleware/errors.js`). The Docker image runs as a non-root `nodeapp` user (`apps/api/Dockerfile`). `.env.example` lists every required secret so operators don't invent insecure defaults blindly. | Operators must still set `NODE_ENV=production` and a real `CORS_ORIGINS` themselves — the app does not hard-fail if these are left at insecure defaults (see production checklist). Helmet's CSP has no `upgrade-insecure-requests` directive since this app itself doesn't serve HTML; a reverse proxy should handle HTTP→HTTPS redirection. |
| A06 | Vulnerable and Outdated Components | On the security branch dated 2026-10-28, `npm audit --omit=dev` reports 0 vulnerabilities in both `apps/api` and `apps/web` on locked dependencies (run [#40702924652](https://github.com/paulafanasyev/svetlana_tutor/actions/runs/40702924652)). API dependency Zod was moved to `^4.6.7`; React Router was moved to `^7.18.5` to address the findings from the initial scan. | Point-in-time result only; dev dependencies and runtime behavior are outside this production-dependency scan. Re-run the audit regularly and after every dependency change. Do not treat this scan as a penetration test. |
| A07 | Identification and Authentication Failures | Login/register are rate-limited more aggressively than the rest of the API (20 requests / 15 min on `/api/auth/*` vs. 300/15min globally — `src/app.js`). The `loginGuard.js` adds a 5-failure per-email+IP lock and a 50-failure per-email aggregate lock, both over a 15-minute window; the lock lasts 15 minutes. Generic login errors, bcrypt, short-lived access tokens, refresh-token rotation/reuse detection and blocked-user checks provide additional controls. | The login guard is in process memory: it resets on process restart and is not shared across replicas. Use a shared store such as Redis before horizontal scaling. No MFA support; no additional password complexity rule beyond minimum length. |
| A08 | Software and Data Integrity Failures | This branch introduces committed `package-lock.json` files for both `apps/api` and `apps/web`. The security workflow now uses `npm ci` before auditing, so dependency installation and audit operate against the locked tree. The API Docker image also uses `npm ci`. JWTs are integrity-protected (HMAC-SHA256) and require a configured strong `JWT_SECRET`. | The lockfiles and the workflow change are not on `main` until this PR is merged. No code-signing/SRI for client assets and no supply-chain attestation (e.g. Sigstore) are configured. |
| A09 | Security Logging and Monitoring Failures | Admin mutations (user block/unblock, role change, deletion, setting changes, material upload/delete) are recorded to the `AdminLog` table with actor, action, and target (`src/middleware/adminLog.js`, invoked from `src/routes/admin.js` and `src/routes/materials.js`). Server errors are logged server-side with method/path/status even in production, without leaking that detail to the client (`src/middleware/errors.js`). Secrets are never logged: JWTs, refresh tokens, and password hashes are excluded from all log statements in `src/`. | No centralized/shipped log aggregation is configured (stdout only) — operators self-hosting via Docker should pipe container logs to their own aggregation stack. No alerting on anomalous patterns (e.g. spike in 401s/403s indicating a credential-stuffing attempt) is built in. |
| A10 | Server-Side Request Forgery (SSRF) | The backend makes **no outbound HTTP requests to user-supplied URLs anywhere** — the materials task generator (`src/lib/taskGenerator.js`) and text extraction (`src/lib/textExtract.js`) are explicitly local/offline (pdf-parse, mammoth, and a hand-rolled stopword-frequency algorithm), by design, so there is no SSRF surface in this feature. | If a future feature adds a "fetch article from URL" import, it must go through an egress allowlist/validator — flag this in review if ever proposed. |

## Additional, non-OWASP-numbered controls implemented

- **Rate limiting and login guard**: global 300 req / 15 min, plus a stricter 20 req / 15 min limiter scoped to `/api/auth/*` (`src/app.js`). `src/lib/loginGuard.js` adds 5 failed attempts per email+IP and 50 failures across IPs per email (15-minute window; 15-minute lock). The guard remains process-local and must use a shared store at multi-replica scale.
- **Upload validation**: `multer` memory storage with a 10MB hard limit and MIME allowlist (`pdf`, `docx`, `txt` only) enforced in `fileFilter` *before* the file buffer is handed to a parser (`src/routes/materials.js`, `src/lib/textExtract.js`), reducing the attack surface for malicious-file parsing exploits.
- **Body size limit**: `express.json({ limit: '1mb' })` in `src/app.js` bounds request payload size, mitigating trivial JSON-bomb style DoS.
- **RBAC enum, not string**: `Role` is a Prisma enum (`STUDENT | TEACHER | PARENT | ADMIN`), so the database rejects an invalid role value — defense in depth beyond the request-schema enum in `src/routes/admin.js`.

## Production Deployment Checklist

Operators self-hosting this backend from the source zip should confirm every
item below before exposing it to real users:

- [ ] **TLS everywhere.** Terminate TLS at a reverse proxy (nginx, Caddy, Traefik, or your cloud LB) in front of the `api` container — this app speaks plain HTTP and assumes TLS is handled upstream. Redirect all HTTP to HTTPS. Enable HSTS at the proxy layer.
- [ ] **Secrets management.** Never commit a real `.env`. Generate `JWT_SECRET` with `openssl rand -hex 64` (not the placeholder from `.env.example`). Set a strong, unique `POSTGRES_PASSWORD` (not the compose default). Prefer a secrets manager (Docker secrets, Vault, cloud KMS) over plain `.env` files on disk for anything beyond local/dev use.
- [ ] **`NODE_ENV=production`.** Confirm this is actually set in the running container — it gates stack-trace suppression in `src/middleware/errors.js`.
- [ ] **`CORS_ORIGINS` locked down.** Set it to the exact origin(s) of your deployed frontend(s); never use `*` or leave it unset in production.
- [ ] **Change the seeded admin password immediately.** `SEED_ADMIN_PASSWORD` defaults to `ChangeMe_123` if unset — set a strong value in `.env` *before* running `npm run seed`, and rotate it again post-seed via the admin UI/API if the default was ever used, even transiently.
- [ ] **Database network isolation.** Postgres should NOT be exposed on a public port in production — remove or firewall the `POSTGRES_PORT` mapping in `docker-compose.yml` (it is published for local dev convenience) so only the `api` service on the compose network can reach it. Use a security group / firewall rule if running Postgres outside compose.
- [ ] **Least-privilege DB user.** The `POSTGRES_USER` used by the app should have privileges scoped to its own database/schema only, not superuser.
- [ ] **Backups configured and automated.** Enable the cron example in `scripts/backup.sh` (nightly `pg_dump`, gzip, 14-day retention is the built-in default — adjust `KEEP` if you need a longer window).
- [ ] **Backup verification.** A backup that has never been restored is unverified. Periodically run `scripts/restore.sh` against a *staging* database (never production) to confirm backups are actually restorable, and that the restored data + `npx prisma migrate deploy` bring the schema back to a working state.
- [ ] **Off-site backup copies.** Sync the `backups/` directory to storage outside the host (S3/GCS/off-site NAS) — a local-disk-only backup does not survive host loss.
- [ ] **Dependency audit on a schedule.** Run `npm audit --omit=dev` (and review `npm outdated`) on a recurring basis post-deployment — this repo's own audit run is a point-in-time snapshot, not a standing guarantee. Update via `npm update`/lockfile bump and re-test.
- [ ] **Log shipping.** Container logs go to stdout; forward them to your logging stack (e.g. via the Docker `json-file`/`journald` driver plus a shipper, or a managed platform) so `AdminLog` entries and error logs are retained and searchable beyond container lifetime.
- [ ] **Resource limits.** Set container memory/CPU limits for `api` and `postgres` in your orchestrator (plain compose does not enforce any by default) to contain the impact of a runaway process or an unexpectedly large upload burst.
- [ ] **Reverse-proxy request limits.** Even with the built-in Express rate limiter, consider proxy-level connection/request limits (e.g. nginx `limit_req`) as a second layer, since the Express limiter is per-process and won't coordinate across multiple `api` replicas without a shared store (e.g. Redis) — if you scale `api` horizontally, swap the in-memory rate-limit store for a shared one.
- [ ] **Restrict Adminer.** The optional `adminer` compose service (profile `tools`) should never run in production, or if it must, put it behind additional auth (VPN, SSO proxy) — it is intended for local development convenience only.
